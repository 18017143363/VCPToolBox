# VCPTavern 注入排序实现细节补遗（Comparator与all_user）

> 头部说明：为避免误触发，本文占位符统一使用*2转义（例如 {*2VCPTavern::rosa}*2）。

## 新增发现背景
在确认“relative先于depth”后，我进一步复读 `VCPTavern.js`，发现两个容易被忽略但很关键的实现细节，值得单独记录。

## 1) relative排序比较器的实现风险
源码：
```js
.sort((a, b) => (a.position === 'before' ? -1 : 1));
```
该比较器只看`a`，不看`b`，不属于标准三态比较器（-1/0/1依据a与b关系）。  
实际效果通常是把`before`推前、`after`推后，但在“同类元素之间”的相对顺序语义上，可读性和可预期性都偏弱。

## 2) all_user注入的索引安全设计
`all_user`分支先收集全部user索引，再“从后往前”`splice`插入。  
这是经典的“防索引偏移”写法，能避免前面插入导致后面索引失真，属于实现质量较高的细节。

## 3) depth=0不生效再次确认
深度注入仍受：
```js
if (rule.depth > 0) { ... }
```
约束，因此`depth=0`在当前实现不会执行。预设编写时要显式避开这一值。

## 4) 配置迁移结论：不要“一刀切全改before”
当预设出现“体感顺序反了”时，不建议把全部规则改成before。更稳的做法是分层：

- **层A（骨架约束）**：`relative + target:system + before`  
  用于角色核心、不可被后文覆盖的总规则。
- **层B（能力说明）**：`relative + target:system + after`  
  用于工具说明、可扩展文档块。
- **层C（对话尾部补丁）**：`relative + target:last_user + after`  
  用于当轮强约束（如最高要求）。

这样能保持可维护性，不会因为全before导致提示词顶部过载、局部说明难定位。

## 5) 工程建议（最小改动）
1. 先不动大量业务规则，只先修复比较器为标准三态。  
2. 抽3条代表性规则做A/B测试（before版 vs after版）。  
3. 观察模型遵循度与回复稳定性，再逐步迁移，不做一次性翻盘。  
4. 保留可回滚快照（presets文件备份）。

