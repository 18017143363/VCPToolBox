## 关键证据
当前 direct stream 分支：
async for chunk in resp.content.iter_any():
    log.info(f"[CHUNK] {chunk[:200]}")
    await out.write(chunk)

说明代理只做原样透传。`[Thinking: ...]` 格式并非代理生成，而是 Dedalus 上游 OpenAI Chat Completions 兼容层返回。

非流式样本：
[Thinking: The user is greeting me in Chinese, saying "Hello."] 你好！很高兴见到你...

流式样本：
[Thinking: The user is greeting me in Chinese, saying "hello." I should respond in Chinese.你好！很高兴见到你...

日志样本显示 Dedalus SSE delta.content 序列大致为：
1. "[Thinking: "
2. thinking 文本片段
3. 中文正文片段
4. 正文继续
5. finish_reason=stop

## 逆向推断
Dedalus 内部很可能将 Anthropic 原生结构化事件映射为 OpenAI chat.completion.chunk：
- Anthropic thinking block start → emit delta.content="[Thinking: "
- Anthropic thinking_delta → emit delta.content=thinking_text
- Anthropic thinking block stop → 应 emit delta.content="] "，但实际漏掉
- Anthropic text_delta → emit delta.content=text

非流式路径能正常闭合，是因为它拿到完整 message blocks 后做最终 stringify：
content = "[Thinking: {thinking}] {text}"

流式路径则是逐事件 mapper，且缺少 thinking_block_stop 或 text_block_start 的 suffix 处理，因此正文直接粘到 thinking 后面。

## 重要结论
这是 Dedalus 上游 chat/completions streaming adapter 的结构信息丢失问题，不是本地代理吞字符。
一旦上游把 thinking_delta 和 text_delta 都拍扁为 delta.content，且不发 `]` 或 block boundary，代理侧无法 100% 确定 thinking 与正文边界。
之前状态机吞正文的根因正是它等待 `]`，但上游流式永远不发闭合符。

## 修复路线评估
1. 原样透传：保留真流式，但前端看到未闭合 `[Thinking:`
2. 假流式：上游 non-stream 后代理合成 SSE，格式稳定但不是真流式
3. 结构化端点：若 Dedalus /v1/messages 能返回 Anthropic native stream，则可按 content_block_start/delta/stop 正确转换为 OpenAI SSE。这是唯一可靠的“真流式+正确边界”方案
4. 启发式修补：按中文/回答开头猜边界，不可靠，不建议作为正式方案

保留当前干净极简注入版本；删除或开关化 [CHUNK] 日志，避免 prompt 泄漏和日志膨胀。后续若继续修，应优先验证 Dedalus 的 Anthropic native /v1/messages 流式事件，而不是继续在 chat/completions 的拍扁 content 上写状态机。
