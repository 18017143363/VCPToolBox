## 三、核心模块深度分析

### 3.1 PaperReader.js — 主入口路由器
- stdin接收JSON → 解析command字段 → switch路由到4个handler → stdout输出JSON
- handleIngestPDF: 校验路径→生成paperId(sha1前10位)→缓存检查(manifest+meta存在即跳过)→调用ingestPdf→chunkMarkdown切分→保存chunks/manifest.json和各chunk_N.md文件
- handleReadSkeleton: 直接调用generateSkeleton()
- handleReadDeep: 调用readDeep()→读取Round_1_Summary.md返回content
- handleQuery: 调用queryPaper()
- 缓存机制：IngestPDF检查workspace/{paperId}/chunks/manifest.json存在则直接返回cached:true，forceReparse可强制重解析

### 3.2 ingest.js — 智能降级解析入口
- 检查MINERU_API_TOKEN是否存在
- 有Token：尝试MinerU云端→成功返回engine:'mineru'→失败打印降级日志后fall through
- 无Token或MinerU失败：调用pdf-parse-fallback→返回engine:'pdf-parse'
- MinerU错误：区分MineruError(自定义错误类)和普通Error

### 3.3 pdf-parse-fallback.js — 降级解析
- 使用pdf-parse v2新API：new PDFParse({ data: Uint8Array })
- Buffer→Uint8Array转换（v2要求）
- getInfo()获取页数 → getText()获取纯文本
- 清理：\r\n→\n，3+连续换行→2个
- 返回：markdown(纯文本), figures:[], pageCount, figureMap:[], degraded:true

### 3.4 chunker.js — 章节感知切分器
核心函数：chunkMarkdown(markdown, options)
- extractSections()：正则匹配#{1,4}提取章节结构，返回[{level, title, content}]
- 每个章节判断token数：
  - ≤targetTokens(默认2000)：整块作为一个chunk
  - >targetTokens：splitAtParagraphs()在段落边界二次切分
- splitAtParagraphs()：按\n\n+分段，超长单段按句子边界再切（。？！.!?\n）
- Meta-Header注入：每个chunk前插入[章节名]+[全局摘要]+[上文衔接:最后200字符]
- overlap机制：每个chunk保留上一个chunk尾部15%的文本作为衔接
- 安全阀：最多120个chunks（DEFAULT_MAX_CHUNKS）
- 导出：countTokens()使用tiktoken cl100k_base编码

### 3.5 skeleton.js — 骨架提取器
核心函数：generateSkeleton(paperId, options)
- 读取full_text.md全文
- extractTOC()：提取所有#{1,4}标题生成目录树（含缩进层级）
- extractKeySections()：正则匹配17种关键章节名（英文+中文）：abstract/introduction/conclusion/discussion/summary/overview/background/preface/executive summary/摘要/引言/结论/讨论/概述/背景/前言/总结
- loadFigureCaptions()：读取figure_map.json获取图注信息
- LLM提取8个要素：核心主题、核心问题、关键内容概要、结构路线图、主要结论、局限性、各章节优先级(High/Medium/Low)、深读建议
- 输出：保存到reading_notes/Global_Map.md

### 3.6 deep-reader.js — Rolling Context深度阅读核心（最大最重要的模块）
核心函数：readDeep(paperId, options)
**Rolling Context机制**：
- 每个chunk摘要后提取key_facts追加到rollingContext字符串
- 格式：[Chunk N - 章节名]: fact1; fact2; fact3
- 上限4000 tokens，超出时调用compressContext()让LLM压缩为关键事实列表(≤2000 tokens)

**批量并发处理**：
- 按batchSize(默认4)分组，同batch内的chunk共享同一份rolling context快照并行处理
- batch间有CHUNK_DELAY_MS(默认1500ms)延迟防止429
- 权衡：BatchSize=1最强上下文递进但最慢，=5推荐甜蜜点，=10+最快但batch内chunk无法互相感知

**增量恢复**：
- 检查已有Chunk_Summaries.json，已有的chunkIndex跳过LLM调用
- 支持中断后继续处理剩余chunks

**缓存检查**：
- Round_1_Summary.md + Chunk_Summaries.json都存在时直接返回cached:true
- forceReread可强制重新阅读

**Chunk摘要格式**（JSON）：
{summary, key_facts[], methods[], claims[], open_questions[]}
- methods：不限于科研实验，包含任何流程/步骤/操作方法
- claims：文档中的核心论断/条款/规定

**最终合成**：
- 所有chunk摘要完成后，将全部摘要+rolling context+global map送入LLM合并
- 输出Markdown格式深度笔记 → 保存到Round_1_Summary.md
- 摘要JSON切片上限150000字符防止超限

### 3.7 skim-reader.js — 轻量扫读器（v0.4新增）
核心函数：skimChunk(chunkText, options)
- 用一句话概括chunk核心内容
- upgrade检测：如果发现与阅读目标高度相关的意外重要内容，标记upgrade:true
- 关键约束：**Skim结果不写入Rolling Context**（不污染精读上下文）
- 返回JSON：{summary, upgrade:boolean, reason}
- LLM限制：max_tokens=500，温度0.1

### 3.8 query.js — 检索式问答
核心函数：queryPaper(paperId, question)
- keywordPick()关键词匹配：问题分词→遍历所有chunk→text包含关键词+1分，section包含+2分→取top6
- 无匹配时fallback到前4个chunk
- 加载Global Map作为全局上下文
- 读取匹配chunk的完整文件内容
- LLM问答：要求先给结论再给证据引用（标注chunk index和章节名），证据不足时明确说"证据不足"
- 返回：{paperId, answer, sources[{index, section}]}

### 3.9 llm.js — LLM调用封装
**API配置优先级**：
- Key: PaperReaderApiKey > Key > API_Key
- URL: PaperReaderApiUrl > API_URL（自动追加/v1/chat/completions）
- Model: PaperReaderModel（必填）

**URL智能修正**：
- 纯localhost/127.0.0.1地址→自动替换端口为VCP_PORT(6005)+追加路径
- 无/v1/路径→自动追加/v1/chat/completions

**重试策略**：
- 最大5次重试
- 仅429触发重试，指数退避：3s→6s→12s→24s→48s
- 单次请求超时180秒

**错误分类器classifyLlmError()**：
| 错误类型 | 触发条件 | 提示信息 |
|---------|---------|---------|
| rate_limit | 429 | 降低并发/增大间隔 |
| auth | 401/403 | 检查API_Key |
| timeout | ECONNABORTED | 提高超时/降低输入体积 |
| upstream_5xx | 500-599 | 稍后重试 |
| network | ENOTFOUND/ECONNREFUSED/EAI_AGAIN | 检查API_URL或网络 |
| unknown | 其他 | 原始错误信息 |

**callLLMJson()**：
- 调用callLLM获取原始文本
- 尝试从markdown代码块中提取JSON（正则匹配```json```）
- JSON解析失败时返回{raw_response: 原文}（优雅降级）

### 3.10 reading-state.js — 阅读状态持久化（v0.4预埋）
**状态结构**：
```
{
  docId, goal, mode:'auto',
  currentPhase: 'survey'|...,
  round: 1,
  rollingContext: '',
  readLog: [{chunkIndex, section, readMode, nodeId, readAt, round}],
  chunkSummaries: [],
  auditReport: null,
  createdAt, updatedAt
}
```
**核心功能**：
- loadOrCreateState()：加载已有状态，goal变化时自动创建新round
- addChunkRead()：记录chunk阅读日志
- addChunkSummary()：添加/去重chunk摘要
- setPhase()：更新阶段
- getReadChunkIndices()：获取已读chunk索引（支持按round过滤）
- 路径：workspace/{docId}/reading_notes/reading_state.json

**注意**：此模块已完整实现但未被当前主入口调用，属于v0.4预埋代码。

## 六、MinerU云端限制
- 每日免费额度：2000页
- 单文件上限：200MB / 600页
- 两种模型版本：pipeline(快速) / vlm(高精度但慢)
- 需要从 mineru.net 获取API Token

## 七、设计亮点
1. **智能降级**：MinerU失败自动降级到pdf-parse，保证功能永远可用
2. **Rolling Context**：chunk间信息传递的核心机制，避免信息孤岛
3. **批量并发+快照隔离**：同batch共享context快照实现并发，batch间串行更新context
4. **增量恢复**：中断后可从已有摘要继续，不浪费已完成的LLM调用
5. **Skim upgrade**：扫读中发现重要内容自动升级为精读
6. **错误分类器**：6种LLM错误类型精准归类，提供明确修复建议
7. **多文档类型适配**：prompt设计不限于学术论文，支持技术报告/书籍/法律文书等
