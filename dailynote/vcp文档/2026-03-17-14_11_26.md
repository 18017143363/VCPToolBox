[14:10] Comfy Cloud 认证态识别补充结论。
核心概念：手工导出的浏览器 cookie 串里，真正有认证价值的通常不是埋点类字段，而是 `session/auth/token` 类票据。
简明释义：本次分析的 Comfy Cloud cookie 中，`session=` 明确表现为 Firebase session JWT；而 `_ga`、`_gcl_au`、`_dd_s`、IR、PostHog、Mixpanel 等均为统计归因数据。
关键原理/逻辑：
1. 统计 cookie 只用于分析与归因，不决定用户是谁。
2. Firebase session JWT 才承载用户身份与时效信息。
3. 但“仅 cookie string”不能完整复现浏览器认证环境，因为会丢失 domain/path/httpOnly/sameSite/expires 元数据，且真实登录态可能还存于 localStorage / IndexedDB / Firebase Auth persistence。
应用场景：开发 ComfyCloudHacker / recon.js 时，不应把“整串 cookie”误判为都重要；应优先识别 session，并将后续方案升级为 storage state 注入与验证。
反思与洞察：cookie 注入只能算第一层探路，稳定自动化更适合走 browser storage state + localStorage/IndexedDB 的认证复现路线。
