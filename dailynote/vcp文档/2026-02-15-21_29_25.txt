# VCP核心机制：AI的"中断与唤醒"详解

## 概述
本文档深入解析VCP处理AI工具调用的核心机制——"中断与唤醒"。此机制确保了AI能在需要外部工具协助时，先暂停回复，等待工具执行结果，再带着结果被唤醒并生成最终答案，整个过程对用户保持流畅透明。

## 核心流程图 (文字版)
```
用户提问 → AI生成包含TOOL_REQUEST的回复
↓
VCP (chatCompletionHandler) 检测到工具请求
↓
【中断】暂停回复流程，不向用户显示
↓
VCP (toolExecutor) 调用对应插件执行工具
↓
插件返回结果 (成功/失败/数据)
↓
【唤醒】VCP用工具结果重新构建消息历史
↓
VCP再次调用AI，此时上下文中已注入工具结果
↓
AI生成最终回复，包含对工具结果的解读
↓
用户看到最终答案
```

## 详细阶段拆解

### 第一阶段：请求与中断
1. **AI响应**：在生成回复时，AI判断需要调用工具，因此在回复末尾嵌入`<*3[TOOL_REQUEST]>*3`块。
2. **VCP拦截**：`chatCompletionHandler`在收到AI的回复后，会解析其内容。一旦发现有效的工具调用请求，它会执行以下操作：
   - **不向用户流式传输**包含工具请求的回复。
   - 将工具请求从AI回复中剥离，并转发给`toolExecutor`。
   - **暂停当前会话的回复流程**，进入等待状态。

### 第二阶段：工具执行
1. **任务分发**：`toolExecutor`根据`tool_name`找到对应的插件，并启动插件进程。
2. **同步/异步处理**：
   - **同步插件**：VCP会阻塞等待插件返回结果。
   - **异步插件**：插件立即返回一个"任务ID"，VCP会定期检查任务状态或等待回调。
3. **结果返回**：无论同步异步，最终`toolExecutor`都会将工具的执行结果（一个JSON对象）返回给`chatCompletionHandler`。

### 第三阶段：唤醒与注入
1. **构建新上下文**：`chatCompletionHandler`拿到工具结果后，会构建一份**唤醒AI所需的消息历史**。这份历史通常包含：
   - 原始对话中的所有消息（用户问题、之前的对话）。
   - AI最后一次回复（即包含工具调用的那条消息）被**替换或增强**，不再显示工具请求，而是显式地注入工具的结果。
2. **再次调用AI**：VCP使用这份新的消息历史，再次向AI发起请求。

### 第四阶段：苏醒与回复
1. **AI感知**：当AI被"唤醒"并收到新的请求时，它的上下文中已经包含了工具执行的结果。它可以像处理普通对话一样，解析这些结果。
2. **生成最终回复**：AI根据用户的原始意图和工具提供的数据，生成最终的自然语言回复。
3. **返回给用户**：`chatCompletionHandler`将这份最终的回复流式传输给用户。

## 唤醒时注入的信息详解
当AI被唤醒时，其接收到的`messages`数组中会注入以下关键信息，通常以`assistant`角色的一条新消息或对原消息的修改形式呈现：

| 字段/内容 | 示例 | 说明 |
| :--- | :--- | :--- |
| **工具调用上下文** | `[TOOL_RESULTS]` 或一段描述性文本 | 一种隐式的系统标记，告诉AI现在是在处理工具结果。 |
| **工具结果数据** | `{"tool_name": "LocalSearchController", "result": ["C:\file1.txt", "C:\file2.txt"]}` | 这是核心数据，通常以JSON格式嵌入在消息内容中，供AI解析。 |
| **原始用户问题** | （存在于之前的`user`消息中） | AI必须记住最初的目标，才能正确使用工具结果。 |

## ⭐ 重要发现：VCP循环直接发给上游AI

### 源码证据 (streamHandler.js)
```javascript
const nextAiAPIResponse = await fetchWithRetry(
  `${apiUrl}/v1/chat/completions`,  // apiUrl = 上游AI地址（如Gemini API）
  {
    body: JSON.stringify({ ...originalBody, messages: currentMessagesForLoop, stream: true }),
  },
);
```

### 关键结论
VCP循环中的再次请求是**直接发给上游AI**的，**不会经过VCP的消息预处理链**！

这意味着：

| 预处理操作 | 首次请求 | VCP循环 |
|-----------|---------|---------|
| VCPTavern注入 | ✅ 执行 | ❌ 不执行 |
| messageProcessor变量替换 | ✅ 执行 | ❌ 不执行 |
| 媒体处理器 | ✅ 执行 | ❌ 不执行 |
| 其他messagePreprocessors | ✅ 执行 | ❌ 不执行 |
| roleDivider | ✅ 执行 | ✅ 可选（enableRoleDividerInLoop） |
| RAG区块刷新 | N/A | ✅ 可选（RAGMemoRefresh） |

### 为什么预设内容还能正常工作？
因为VCPTavern在首次请求时已经把预设内容**写入了messages数组**。StreamHandler通过 `currentMessagesForLoop = originalBody.messages` 继承了这些已处理好的messages，后续循环只是追加工具结果，不会删除已有内容。

## 设计意义
1. **解耦**：AI的思考逻辑与工具的执行逻辑完全分离，使系统更模块化。
2. **流畅性**：用户不会感知到工具调用的"卡顿"或中间状态，体验如同连续对话。
3. **可靠性**：通过完整的"请求-执行-结果"闭环，确保了工具调用过程的原子性和可追踪性。
4. **性能**：VCP循环中跳过预处理链，避免了重复的变量替换和预设注入，提升效率。
