[15:23] Dedalus代理新增BYPASS流式上游空回自动重试机制

## 问题背景
主人反馈通过NewAPI使用ChatBox调用`gpt-5.4(xhigh)`长输入时（几千字prompt）出现空回。但同一NewAPI渠道，VCP正常、curl正常、短输入正常。

## 诊断过程
1. 直接curl打代理同款请求：HTTP 200, 2154字节SSE，完整delta（Hi! How can I help...）→ 代理本身没问题
2. 查proxy.log发现：
   - Go-http-client客户端多次"0 chunks空回"，1.9-2.2秒就结束
   - 一次`TransferEncodingError: 400, message='Not enough data to satisfy transfer length header.'`
   - 一次60秒后0字节
   - 但同一时间curl测试可以拿到正常数据
3. 关键证据：上游Dedalus对xhigh+长输入的稳定性差，会出现"声明chunked但body不发"的情况
4. ChatBox空回但VCP不空回的差异：VCP带fetchWithRetry会自动重试

## 真正根因
Dedalus上游对xhigh+长请求的流式响应不稳定，偶发"200但空body"或"中途断流"。代理之前没有重试机制，客户端拿到无内容的SSE就显示空回。

## 修复方案：预读首字节 + 空回自动重试

### 设计约束
- `out.prepare(req)`一旦执行，响应头就发给客户端了，不能再切换上游
- 必须在prepare之前发现"上游空回"

### 三步改造（22832 → 25987字节，+3155）

#### 步骤1：新增异常类+配置常量
```python
class UpstreamEmptyStream(Exception):
    def __init__(self, key, reason=""):
        self.key = key
        self.reason = reason

BYPASS_STREAM_FIRST_BYTE_TIMEOUT = 35  # 秒
BYPASS_STREAM_MAX_RETRIES = 3
```

#### 步骤2：BYPASS流式分支预读首字节
```python
if is_stream and resp.status == 200:
    first_chunk_bytes = None
    if do_bypass:
        try:
            first_chunk_bytes = await asyncio.wait_for(
                resp.content.read(1),
                timeout=BYPASS_STREAM_FIRST_BYTE_TIMEOUT,

            raise UpstreamEmptyStream(key, "zero bytes from upstream")
```

#### 步骤3：handle_proxy的retry循环捕获并重试
```python
except UpstreamEmptyStream as e:
    if attempt + 1 >= BYPASS_STREAM_MAX_RETRIES:
        log.warning("[UPSTREAM-EMPTY] giving up after %d attempts", attempt + 1)
        return web.json_response(
            {"error": {"message": "Upstream returned empty stream after retries: " + e.reason,
                       "type": "upstream_empty_stream"}}, status=502)
    log.warning("[UPSTREAM-EMPTY] retry attempt %d | key=...%s | reason=%s",
                attempt + 2, e.key[-8:], e.reason)
    async with pool.lock:
        if pool.keys:
            pool.idx = (pool.idx + 1) % len(pool.keys)
    continue
```

## 关键设计决策

1. **不删除key**：上游不稳定不是key的错，删key会浪费可用资源
2. **轮换pool.idx**：避免连续命中同一个被Dedalus限流的key
3. **首字节超时35秒**：xhigh通常3-4秒首字节，留足余量给长输入
4. **最多3次重试**：避免无限循环
5. **502兜底**：3次都失败时返回明确错误，方便客户端识别

## 重试流程
```
请求 → key1 → 预读首字节 → 35s无数据
  → UpstreamEmptyStream raise
  → 外层捕获 → 轮换到key2 → 重新请求
  → 预读首字节 → 拿到首字节
  → prepare() → 正常stream → 客户端收到完整数据
```
客户端整个过程透明，只是延迟稍长。
