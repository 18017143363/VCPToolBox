## 背景
主人在调用 `anthropic/claude-opus-4-6` 时，前端仅显示：
```json
{
  "error": {
    "message": "openai_error",
    "type": "bad_response_status_code",
    "code": "bad_response_status_code"
  }
}
```
但代理日志中真实上游错误为：
```text
[UPSTREAM_ERROR] status=422 | path=/v1/chat/completions | model=anthropic/claude-opus-4-6 | body={
  "detail": [{
    "type": "json_invalid",
    "loc": ["body", 563],
    "msg": "JSON decode error",
    "ctx": {"error": "Invalid \\uXXXX escape"}
  }]
}
```

## 根因判断
该错误发生在 Dedalus 上游 JSON parser 阶段，说明 HTTP body 不是合法 JSON。它不是：
- Claude thinking 参数语义错误
- max_tokens 与 thinking.budget_tokens 预算错误
- `/v1/messages` 或 `/v1/chat/completions` 路由错误

而是请求体第 563 字符附近存在非法反斜杠转义，如：
```text
C:\Users
\usepackage
\d+
\x
坏的 \u
```
在 JSON 字符串中，反斜杠只能用于合法 escape：
```text
\" \\ \/ \b \f \n \r \t \uXXXX
```
其中 `\u` 后必须是 4 位十六进制字符。

## 外部资料检索结论
通过 VSearch Tavily 检索确认：
1. `Invalid \uXXXX escape` 通常不是 aiohttp bug，而是请求体本身非法。
2. 透明代理最好不解析不需要理解的 JSON，直接 raw bytes 转发。
3. 但当前 Dedalus 代理必须解析/改写 JSON（Claude thinking 注入、responses reasoning 映射），因此需要严格 JSON 验证。
4. 不建议全局：
```python
body.replace("\\", "\\\\")
```
因为会破坏合法 escape，例如 `\n`、`\"`、合法 `\u4e2d`。
5. 可接受方案是“只修复 JSON 字符串内部非法 escape”，并且修复后必须再次 `json.loads()` 验证。

## 新增函数

### 1. `_snippet_around(text, pos, radius=120)`
用于记录 JSONDecodeError 位置附近文本，便于排查：
```python
snippet = _snippet_around(text, first_error.pos)
```

### 2. `escape_invalid_json_backslashes(s: str) -> str`
功能：
- 只在 JSON 字符串内部处理反斜杠。
- 保留合法 JSON escape：
```text
\" \\ \/ \b \f \n \r \t \uXXXX
```
- 将非法 escape 转为字面反斜杠，例如：
```text
\U -> \\U
\d -> \\d
\x -> \\x
坏的 \u -> \\u
```
- 不处理字符串外部内容，降低误改风险。

### 3. `validate_or_repair_json_body(raw: bytes, path: str) -> tuple[bytes, web.Response | None]`
处理流程：
1. 空 body：直接放行。
2. `json.loads(raw)` 成功：直接放行。
3. JSONDecodeError：
   - decode UTF-8；
   - 记录：
```text
[BAD_JSON] initial parse failed | path=... | len=... | msg=... | line=... | col=... | pos=... | snippet=...
```
   - 调用 `escape_invalid_json_backslashes(text)`。
4. 若修复后与原文相同：返回本地 400 `invalid_json`。
5. 若修复后仍不能 `json.loads()`：返回本地 400 `invalid_json_repair_failed`。
6. 修复成功：
```text
[BAD_JSON] repaired invalid JSON backslash escapes | path=... | original_len=... | repaired_len=...
```
   并返回修复后的 UTF-8 body 继续代理。

## 预期效果
如果请求体中存在常见裸反斜杠问题，代理会尝试修复后继续转发，不再让 Dedalus 返回：
```text
422 json_invalid Invalid \uXXXX escape
```

如果修复失败，前端将得到本地清晰错误，而不是上游包装后的 `bad_response_status_code`：

## Python 源码层踩坑
初始补丁在 helper docstring 中写了裸：
```text
\uXXXX
\U
\x
```
导致 Python 解释器在源码解析阶段报：
```text
SyntaxError: (unicode error) 'unicodeescape' codec can't decode bytes ... truncated \uXXXX escape
```
这与本次 JSON 错误属于同类“字符串层反斜杠转义”问题。修复方式是移除 docstring 中裸反斜杠示例，改成安全描述。最终执行：
```powershell
python -m py_compile .\dedalus_proxy.py
```
返回：
```text
PY_COMPILE_OK
```

## 注意事项
1. 这是兼容坏客户端的兜底，不是长期根治。
2. 根治应检查请求生产方（酒馆/NewAPI/中间层）是否手写 JSON，是否未使用标准 JSON serializer。
3. 若日志出现 `[BAD_JSON] initial parse failed`，应根据 snippet 定位具体非法内容。
4. 不建议无审计地长期吞掉所有坏 JSON；后续可增加 repair 计数、开关或 debug dump 文件。

## 经验教训
1. 代理层做 JSON 变换时，必须考虑坏 JSON 输入，否则 `json.loads` 失败后原样转发会把错误推迟到上游。
2. JSON repair 必须“只修非法 escape”，不能全局替换反斜杠。
3. Python 源码 docstring 本身也会处理反斜杠，写 `\uXXXX` 这类占位符时要用 raw string 或避免裸写。
