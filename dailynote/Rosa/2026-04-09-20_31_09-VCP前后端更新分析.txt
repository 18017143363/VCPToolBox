[22:08] 虚拟机完整测试日志分析 — 发现两个独立bug
主人给了完整install_log，暴露两个问题：
### Bug1: git pull VCPToolBox失败
日志：`error: Your local changes to start_server.bat would be overwritten by merge`
根因：上一次installer的generate_inner_start_bat()覆盖了VCPToolBox/start_server.bat→本地有未提交修改→git pull拒绝合并
修法：git_ops.rs git pull前加`git checkout -- .`丢弃本地修改
### Bug2: PM2"已安装"但bat找不到
日志：`[npm] PM2 已安装，跳过`
根因：旧版installer无--prefix，pm2.cmd装到%APPDATA%\npm→双重检测第二层(cmd /c pm2 --version)走系统PATH命中→跳过→但runtimes\node下没pm2→start_server.bat PATH找不到→闪退
修法：PM2检测只认runtimes\node\pm2.cmd文件，删掉命令行兜底检测

[22:40] Bug3: bat中文乱码导致闪退
主人发来虚拟机上start_server.bat内容，中文全是GBK乱码（鍚庣鏈嶅姟鍚姩鍣?）
根因：Rust fs::write()输出UTF-8，但cmd.exe读取bat文件用系统默认编码GBK。chcp 65001只影响输出显示，不影响bat文件本身的读取编码。乱码字符可能被解析为特殊bat符号导致执行异常。
修法：config_gen.rs里所有bat内容的中文改为英文（inner版+外层版都改了）

[23:00] Bug4: bat调pm2.cmd不加CALL导致控制流一去不返
主人反馈bat闪退——clean之后就没了。
根因：bat里`pm2 delete`实际执行pm2.cmd，bat调bat不加CALL控制流转移后不返回。第一个pm2 delete执行完整个bat就结束了。
修法：所有pm2命令前加CALL（generate_start_backend_bat 6处 + generate_inner_start_bat 6处）
经典bat大坑！VChat的`call npm start`早就写对了，只有PM2的漏了。
注意：主仓库的start_server.bat也没加CALL，作者可能忘了也可能靠PM2内部处理。但portable环境下pm2.cmd是npm的wrapper脚本，必须CALL。

[23:09] config_gen.rs PowerShell正则替换破坏UTF-8编码事故
PowerShell的Get-Content+Set-Content替换pm2→CALL pm2时，把文件编码搞坏了（bytes [231,154] not valid utf-8）。
根因：PowerShell Set-Content默认编码不是UTF-8，会破坏中文字符。
恢复方式：git checkout HEAD恢复原版→FileOperator EditFile一次性写入完整新版文件
教训：**永远不要用PowerShell的Set-Content修改Rust源码文件！** 用FileOperator的EditFile/WriteFile代替。
最终config_gen.rs改动：
1. generate_start_backend_bat: 中文→英文 + node server.js→PM2双进程 + pm2加CALL
2. generate_start_frontend_bat: 中文→英文
3. generate_inner_start_bat: 中文→英文 + PM2双进程 + pm2加CALL + VCPChat start.bat加PATH注入
