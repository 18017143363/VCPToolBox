### 卡在writeJSON函数——BAD CSRF
POST请求总返回403 BAD CSRF。Rosa迭代了6种方案：
1. fetch credentials:include → session cookie触发CSRF
2. fetch credentials:omit → 浏览器自动带Origin header，Discourse仍走浏览器路径
3. request interception删Cookie → Chromium协议层仍注入Cookie
4. 双page方案 → 同上
5. CDP Fetch domain → timeout
6. Node.js https → CF TLS指纹拦截

根因：Puppeteer浏览器环境内的fetch**无法去掉Origin header**（安全策略），Discourse对有Origin的请求强制CSRF检查，即使带了User-Api-Key。
API Key认证本应不需要CSRF，但只对"无Origin header的请求"生效。

## [22:00] 写操作BAD CSRF终于攻克！credentials:'omit'一招制敌！
### 根因
Puppeteer page.evaluate里的fetch用credentials:'include' → 自动带浏览器Cookie → Discourse走session认证路径 → 强制CSRF检查 → 403 BAD CSRF
### 解决方案
```javascript
credentials: 'omit'  // 不带Cookie → Discourse走User-Api-Key认证路径 → 跳过CSRF！
```
一行代码解决了折腾6种方案的问题。VSearch搜索到Discourse源码(application_controller.rb)确认：有效API Key + 无Cookie = 跳过CSRF。

## [21:55] VSearch搜索突破——BAD CSRF根因确认！
搜索Discourse API文档和社区讨论，发现关键信息：
### 核心发现
1. Discourse后端(application_controller.rb)：检测到有效API Key header → 自动跳过CSRF检查
2. **Cookie干扰是根因**：如果请求带了浏览器Cookie → Discourse走session路径 → 强制CSRF
3. Rosa之前所有方案都带了Cookie（credentials:'include'或Puppeteer自动注入的CF cookie）
4. 正确做法：**请求必须"干净"——有User-Api-Key但无Cookie**
### 解决方案
- Puppeteer先过CF（page.goto warmup）
- 用request interception在POST请求时**删除Cookie header**
- setExtraHTTPHeaders伪造Origin为论坛域名
- fetch credentials:'omit' + 手动加User-Api-Key header
