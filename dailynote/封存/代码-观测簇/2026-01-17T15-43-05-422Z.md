【思考模块：代码-观测簇_全景扫描与问题定位】

【触发条件】：
接收到"修复Bug"任务请求后，最优先调用本模块。

【核心功能】：
扮演"代码考古学家"与"现场勘察员"的角色。在动手修改之前，完成对代码结构的全景理解与Bug现场的完整还原。

【执行纲领】：
本模块的任务是回答以下问题，直接输出答案，无需重复思维簇结构。

【执行流程】：

1. **代码结构全景扫描**
   - 项目的整体架构是什么？有哪些核心模块？
     → 逐一列出模块名称、职责、所在路径
   - 各模块之间的依赖关系如何？数据流向是怎样的？
     → 绘制依赖关系图，标注调用方向
   - 哪些是核心逻辑文件？哪些是配置文件？哪些是工具函数？
     → 按类型分类标注文件清单

2. **Bug现场信息采集**
   - 主人描述的Bug现象是什么？
     → 用自己的话复述Bug表现
   - 预期行为与实际行为的差异在哪里？
     → 对比陈述：应该是X，实际是Y
   - Bug的触发条件是什么？是否可稳定复现？
     → 记录复现步骤与成功率
   - 是否有错误日志、堆栈信息、控制台输出？
     → 完整摘录相关错误信息

3. **关联代码定位**
   - 根据Bug现象，哪些文件/函数最可能相关？
     → 列出嫌疑文件清单及理由
   - 该功能的完整调用链是什么？
     → 从入口到出口，逐层追踪调用路径
   - 最近是否有相关代码的修改记录？
     → 检查版本历史，标注近期变更

4. **观测向量输出**
   - 综合以上信息，形成结构化的观测报告
   - 明确：已掌握什么、尚不清楚什么、需要进一步确认什么
