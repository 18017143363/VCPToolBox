# 修Bug思维簇设计与写入记录

## 任务背景
主人要求为"修Bug"场景设计一套完整的思维簇，用于指导代码调试与修复工作。

## 设计要点

### 核心理念
1. 思维簇的本质是**方向性指导**，而非替代正文
2. 每个执行步骤采用"提出问题 → 回答问题"的结构
3. 输出是方向性大纲，由正文进行扩写
4. 沉思簇只规划步骤，不执行实际修改
5. 正文修改文件时，每一步都需要先备份原文件
6. 正文输出的最后必须是日记整理

### 五簇架构

| 簇名称 | 核心角色 | 主要任务 |
|--------|----------|----------|
| 观测簇 | 代码考古学家 + 现场勘察员 | 全景扫描代码结构，采集Bug现场信息，定位关联代码 |
| 拓想簇 | 假设生成器 + 方案建筑师 | 发散原因假设，分析关联影响，设计修复方案 |
| 辩证簇 | 红队质疑者 + 仲裁法官 | 验证假设，审查方案可行性，裁决最终方向 |
| 沉思簇 | 行动规划师 + 安全督导员 | 细化修改步骤，确认安全措施，制定验证计划 |
| 方向簇 | 导航员 + 大纲撰写者 | 归纳成果，生成输出大纲，指引日记整理 |

### 执行纲领的重要性
每个模块都添加了【执行纲领】，明确告知：
- 本模块的任务是回答问题
- 直接输出答案，无需重复思维簇结构
- 沉思簇特别强调：只规划步骤，不执行代码修改

### 安全措施
沉思簇中明确要求：
- 每个文件修改前必须备份
- 备份命名格式：原文件名.backup.时间戳
- 必须有明确的回滚方案

## 写入结果
已成功写入以下五个思维簇文件（文件夹名称以"代码-"为前缀）：
1. 代码-观测簇 → 代码-观测簇_全景扫描与问题定位
2. 代码-拓想簇 → 代码-拓想簇_原因发散与方案孵化
3. 代码-辩证簇 → 代码-辩证簇_假设验证与方案裁决
4. 代码-沉思簇 → 代码-沉思簇_行动规划与步骤确认
5. 代码-方向簇 → 代码-方向簇_成果归纳与输出导航

## 经验总结
1. 思维簇命名应统一前缀（如"代码-"），便于分类管理
2. 执行纲领能有效防止AI在输出时重复思维簇结构
3. 将"自省簇"改为"方向簇"更符合其实际功能——为正文输出提供导航
4. 安全措施（备份、回滚）应在沉思簇中明确规定，而非正文临时决定
